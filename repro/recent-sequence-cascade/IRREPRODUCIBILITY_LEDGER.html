Irreproducibility Ledger

Constitution C3 requires that anything not deterministically reproducible inside the package be marked [O] with its specific obstacle stated, and that these be consolidated in one place. This is that place. The single most important thing it does is keep two very different kinds of [O] from being confused: a real obstacle that blocks a computation, versus a deliberate epistemic cap that the framework is built to enforce.

Part B — [O] by firewall design (NOT irreproducibility)

The entries below are [O] by constitutional design, not because anything is missing. How to read the [O] badge count

The canonical HTML body currently carries 172 [O] badge instances (alongside 40 [F], 109 [V], 51 [L]). The overwhelming majority are Part B firewall caps — the same occurrence cap restated wherever a past-occurrence statement appears — not Part A obstacles. Only the eight Part A rows above are genuine reproduction obstacles. An auditor should therefore read a high [O] count as evidence of a strict, consistently-applied firewall, not as 172 unsolved computations.

Canonical-format note

VP-SPEC v1.9 refers to this file as IRREPRODUCIBILITY_LEDGER.md. This package’s Constitution C2 makes HTML the single canonical body, and the spec itself forbids bundling parallel non-canonical sources. The ledger is therefore delivered as IRREPRODUCIBILITY_LEDGER.html so it stays inside the canonical format and is reachable from the same navigation and stylesheet as every other page. This is a deliberate, stated mapping (markdown name → canonical HTML), not an omission. The authoritative remaining-task list it draws from is OPEN_FRONTIER.html; the per-concept [O] entries are mirrored in /concepts/.
